# C08 · API, database & accounts

> ⏱ ~14 hours · Lessons: 15, 16, 17, 19.4, 20.5 · Course exercises to reuse: 15-03, 15-04, 16-03, 16-04, 17-01, 17-02, 17-03, 17-04, 19-01

## Why
Accounts are what make cross-device play possible. You've built every piece of this in exercises; now it becomes a real, secure service with a real database. It's also the milestone that most clearly says "full-stack" on your CV.

## User stories

### US-1 · A proper API foundation
*As the developer, I want a server that's structured, configured and observable from day one.*

**Acceptance criteria**
- [ ] `createApp(deps)` with dependencies injected (15.6). `src/index.ts` is the composition root.
- [ ] Config from `loadConfig(process.env)` (19-01), which fails fast at startup with a clear message.
- [ ] Middleware in the order given in [ARCHITECTURE §6.1](../ARCHITECTURE.md#61-composition-156): `helmet`, `trust proxy`, pino-http with request ids and redacted cookies (20.5), a JSON limit, `cookieParser`, validation (15-03), and the central error handler (15-04).
- [ ] `GET /api/health` checks the database.
- [ ] Graceful shutdown on `SIGTERM`: stop accepting connections, finish in-flight requests, close the database pool.

### US-2 · A real database
*As the developer, I want schema changes to be versioned and repeatable.*

**Acceptance criteria**
- [ ] A Drizzle schema for `users` and `sessions` (and `saves`, `save_history` and `skill_xp`, ready for C09), as in [ARCHITECTURE §6.3](../ARCHITECTURE.md#63-database-161-175-181).
- [ ] Migrations generated by drizzle-kit, **reviewed and committed**, and applied by a script or at startup (20.3).
- [ ] Local development uses Postgres (Docker, 16.5). Tests use PGlite with a fresh schema per test, like the course's `useTestDatabase` helper.
- [ ] Usernames are unique case-insensitively (a unique index on `lower(username)`).

### US-3 · Accounts
*As a player, I want to create an account and log in securely.*

**Acceptance criteria**
- [ ] `register`, `login`, `me`, `logout` and `logout-all` with the behaviour and error codes of exercise 17-03.
- [ ] Passwords are hashed with your 17-01 scrypt hasher, and checked against the password policy (17-01 `checkPasswordPolicy`). A rehash happens on login when the parameters change.
- [ ] Sessions use your 17-02 session manager with a **Postgres** `SessionStore` (hashed tokens, sliding expiry).
- [ ] The cookie is `HttpOnly`, `SameSite=Lax`, `Secure` from config, and `__Host-` prefixed in production (17.4).
- [ ] Login and registration are rate-limited (17-04) by IP and username. `429` responses include `Retry-After`.
- [ ] The Origin check from 17.6 protects state-changing requests.

### US-4 · Accounts in the game
*As a player, I want logging in to fit naturally into the game.*

**Acceptance criteria**
- [ ] `useMe()` (17.8). The header shows the username when logged in, or a subtle "Guest · Create an account to sync" when not.
- [ ] Login and register pages with proper labels, `autocomplete` values, show-password toggles, inline errors and loading states (17.8). Server errors (`USERNAME_TAKEN`, `INVALID_CREDENTIALS`, `RATE_LIMITED`) are shown in plain language.
- [ ] After login, the player returns to where they were (only relative paths are accepted).
- [ ] Logout clears the query cache. The game continues as a guest (C09 decides what happens to the save).
- [ ] The game is **fully playable without an account**. Nothing is gated behind login except sync.

### US-5 · Leaving
*As a player, I want to be able to delete my account and data.*

**Acceptance criteria**
- [ ] `DELETE /api/account` requires the current password, deletes the user (cascading to sessions and saves) and clears the cookie.
- [ ] Settings has "Delete account", with a confirmation dialog explaining what will be deleted.

## Tests to write
- supertest + PGlite for every route, success and failure: validation, conflicts, wrong passwords, expired sessions, rate limits, deletion cascades.
- Repositories against PGlite (16-04 style).
- Frontend: login and register forms with MSW (errors displayed, redirects, guest banner).

## Hints (directions, not code)
- You've written nearly all of this. The work is adapting it: swapping test doubles for real implementations behind the same interfaces (15.6). If a test from an exercise still applies, port it.
- Start with the database and repositories, then services, then routes, then the frontend, testing each layer before the next.
- The `SessionStore` interface from 17-02 maps directly onto the `sessions` table: write a Drizzle implementation and run 17-02's tests against it.
